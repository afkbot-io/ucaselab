# Выполнение проверки

Получи или используй актуальный контекст проекта и testing policy. Проверь доступность целевого приложения и своих инструментов. Платформа хранит сценарии и результаты; браузер, устройство или API-инструменты предоставляет проверяющий агент.

## Выбор работы

Для нового прямого прогона выбери case_source: published по умолчанию, draft — когда поручено проверить черновики. preview_run возвращает состав и selection_hash для create_run. Проверка черновика не требует его публикации: прогон закрепляет рабочую ревизию и доступен QA. В дальнейшем используй снимок прогона, даже если черновик изменился.

До первого begin_run_check нового прогона вызови get_run_readiness. Проверь фактический адрес стенда, доступы аккаунтов, почту/CAPTCHA и свои инструменты. confirm_run_readiness сохраняет checks {environment,accounts,dependencies}, expected_version и наблюдение; actual_base_url исправляет только адрес снимка. ready означает реально проверенную готовность, not_required — условие не нужно выбранным проверкам. Если выполнить можно только часть, явно укажи allow_partial=true и notes с ограничениями; неподтверждённые условия не становятся ready. Ошибочный адрес и отсутствие инструментов не являются ошибками приложения.

Если пользователь дал run_id или попросил продолжить прогон, используй его: get_run_overview показывает прогресс и next_action; list_run_checks ищет очередь постранично; get_run_check читает один закреплённый вариант. Новый create_run нужен только для нового порученного запуска. Для плана сначала preview_case_plan, затем передай plan_revision_id как expected_plan_revision_id и selection_hash в create_run.

begin_run_check запускает подготовленный прогон и берёт доступный вариант либо возвращает свою уже начатую проверку. Можно явно выбрать run_item_id. Исполнитель определяется пользователем токена. Не меняй чужое назначение и не отбирай занятую проверку без соответствующего поручения. Занятый общий тестовый аккаунт требует ожидания или другой доступной работы; пустой ответ не повод бесконечно опрашивать сервер.

## Наблюдение и итог

Выполни закреплённые шаги на указанных данных. Не подменяй закреплённую ревизию другой версией. record_step_result сохраняет наблюдение шага; либо передай step_results целиком в finish_run_check(execution_id, status, actual_result, step_results, external_issue_url).

- passed — наблюдение совпало, включая правильный отказ на отрицательных данных. Каждый закреплённый шаг должен быть passed; неполный набор даёт STEPS_INCOMPLETE без частичной записи.
- failed — ошибка приложения при подтверждённом ожидании; scenario_issue — сценарий устарел, неоднозначен или не содержит нужных шагов/данных. Укажи спорный шаг и фактическое поведение; не меняй ожидание ради успешного результата. blocked — выполнить не удалось из-за доступа, стенда, данных или инструментов; skipped — осознанный пропуск с причиной. Не выдавай чтение кода или отсутствие ошибки инструмента за успешное тестирование.
- Доказательства прикладывай до итога: add_execution_evidence — до 2 МБ base64; multipart /api/projects/{project_id}/attachments/upload?execution_id=... — до 20 МБ. Bearer только в заголовке. Пароли раскрывай непосредственно для разрешённого шага, не сохраняй в файлах и результатах.

После finish_run_check используй возвращённый run.next_action. Следующий вариант не запускается автоматически. Для следующего выполнения вызови begin_run_check явно. Идемпотентный повтор использует прежний ключ только с теми же аргументами.

Итог неизменяем. Для повторной проверки в активном прогоне используй begin_run_check с run_item_id и retry=true; add_execution_annotation добавляет пояснение без перезаписи. После всех результатов заверши порученный прогон отдельным complete_run с актуальным expected_version; 100% записанных фактов не означает всеобщий успех. После закрытия нужен новый прогон. Отчёт создавай, если нужен по задаче; для активного прогона — interim=true.
