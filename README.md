# UCaseLab

Самостоятельно развёртываемая платформа юзер-кейсов для тестировщиков, разработчиков и ИИ-агентов. Один юзер-кейс описывает функционал, его шаги, ожидания и положительные/отрицательные варианты данных.

В приложении работают регистрация с подтверждением почты, вход по паролю или ссылке, проекты и четыре роли, папки, спецификации, зашифрованные тестовые аккаунты, версии и diff, предложения изменений, обсуждения, планы, прогоны, история проверок, доказательства, отчёты PDF/CSV/JSON, уведомления и персональный MCP-доступ. Баг-трекер не входит в модель: наблюдения сохраняются в результате выполнения, внешняя задача — ссылкой.

Стек: FastAPI, SQLAlchemy/Alembic, PostgreSQL 17, React/TypeScript, Vite, Tailwind CSS, SMTP worker, официальный Python MCP SDK. Зависимости зафиксированы в `uv.lock` и `apps/web/package-lock.json`.

## Быстрый локальный запуск в контейнерах

Нужны Docker с Compose v2 и Python 3.12–3.14 для генерации ключей и упаковки навыков.

```bash
python3 scripts/init_env.py
python3 scripts/package_skills.py
docker compose -f compose.yaml -f compose.dev.yaml -f compose.local.yaml up -d --build
```

- Приложение: http://localhost:8080
- Локальная почта Mailpit: http://localhost:8029
- Готовность backend: http://localhost:8080/api/health/ready

Зарегистрируйтесь через интерфейс и откройте письмо в Mailpit. Создайте проект: создатель становится его руководителем. Затем добавьте окружение, сценарии и опубликуйте первую версию. Демонстрационные пользователи и результаты в новую базу автоматически не добавляются.

В локальном режиме письма перехватываются Mailpit. Для сервера настройте настоящий SMTP и HTTPS по [инструкции развёртывания](docs/DEPLOYMENT.md).

## Production: установка и обновление

Нужны Linux, Python 3.12–3.14, Docker Engine с Compose v2, домен и HTTPS-прокси.
Исходный архив релиза содержит код и готовые пакеты навыков; при установке из Git
сначала соберите их командой `python3 scripts/package_skills.py`.

1. Выполните `python3 scripts/init_env.py`: он создаст `.env` с уникальными ключами
   и правами 0600. Существующий файл не перезаписывается. Не помещайте его в Git.
2. В `.env` задайте `ENVIRONMENT=production`, `PUBLIC_URL=https://qa.example.com`,
   `COOKIE_SECURE=true`, `ALLOWED_HOSTS=qa.example.com,api,localhost`,
   `ALLOWED_ORIGINS=https://qa.example.com`, `HTTP_PORT=127.0.0.1:8080`.
   Сохраните сгенерированные ключи и пароль БД. Настройте SMTP либо явно задайте
   `EMAIL_ENABLED=false`; без почты вход доступен по паролю, ссылки восстановления не отправляются.
3. Проксируйте домен по HTTPS на `127.0.0.1:8080`, передавайте Host, отключите
   buffering для `/mcp/` и задайте timeout не менее 300 секунд. Ограничьте
   `TRUSTED_PROXY_CIDR` адресом доверенного прокси по [подробной инструкции](docs/DEPLOYMENT.md).
4. Запустите `docker compose up -d --build`, затем `docker compose ps` и
   `curl -f https://qa.example.com/api/health/ready`. Используйте основной
   `compose.yaml`; файлы dev/local предназначены для разработки. Успешно завершившийся
   одноразовый контейнер `migrate` — ожидаемое состояние.
5. Зарегистрируйтесь и создайте проект. При включённой почте подтвердите адрес.

Перед обновлением выполните `bash scripts/backup.sh /защищённый/каталог` из
прежнего релиза: копия приостанавливает работающие сервисы и возвращает их прежний
состав. Она содержит БД, вложения и секретный `environment.env`; храните её отдельно
и закрыто. Сохраните имена Compose-проекта/БД/томов и прежние `SECRET_KEY`/`ENCRYPTION_KEY`.
Подготовьте новый релиз, примените прежнюю конфигурацию и выполните
`docker compose up -d --build`, затем проверьте готовность и вход.

Для отката сохраните прежние образы и исходники. Возврат одного кода допустим
только при совместимой схеме БД; иначе восстановите согласованную копию по
[инструкции backup/restore](docs/DEPLOYMENT.md). `docker compose down -v` удаляет данные
и не является способом обновления. Регулярно проверяйте восстановление в отдельном окружении.

## Разработка

```bash
python3 scripts/init_env.py
uv sync --frozen --python 3.13
make dev-db
make migrate
cd apps/web && npm ci
```

В отдельных терминалах из корня: `make api`, `make worker`, `make web`. Интерфейс доступен на http://localhost:5173, API — 127.0.0.1:8017. Письма — в Mailpit на 8029.

```bash
make test
```

Тесты используют PostgreSQL из `.env`, выполняются в откатываемых транзакциях и не стирают существующие проекты. Миграции должны быть применены заранее. CI создаёт отдельную PostgreSQL service database.

## MCP и навыки

В профиле откройте «MCP-доступ», создайте персональный токен с нужными проектами и разрешениями. Endpoint: `https://ваш-домен/mcp/`, транспорт Streamable HTTP, заголовок `Authorization: Bearer …`. Токен показывается один раз и отзывается отдельно от остальных. Роль и членство перепроверяются при каждом вызове.

Девять навыков скачиваются в профиле на вкладке «Навыки для агента»; инструкции конкретного проекта — в настройках или как `ai.md`. Платформа передаёт сценарии и сохраняет результаты; агент использует собственный браузер, устройство или API-инструменты для фактического тестирования.

Для проверок доступно рабочее место с очередью вариантов, явным результатом и прогрессом сохранения. В MCP используйте get_run_overview, begin_run_check и finish_run_check: они возвращают следующее действие и сохраняют шаги вместе с итогом.

## Проверка качества

`make test` выполняет pytest, Ruff, проверку Python через mypy (включая тела функций без аннотаций), проверку ссылок и согласованности документации, строгую проверку TypeScript и production build. Это не означает полную строгую типизацию Python: динамические JSON-снимки и генерируемый реестр содержат `Any`; типы неподдерживаемых сторонних библиотек пропускаются.

После изменения операций выполните `uv run --frozen python scripts/generate_api_schema.py`; после изменения навыков увеличьте их версию и выполните `make skills`. Существующий опубликованный ZIP нельзя перезаписывать другим содержимым. Актуальная схема содержит описание каждой операции, её разрешения и строгие аргументы.

Регрессии, проверенные перед выпуском, и границы браузерного тестирования перечислены в [VERIFICATION.md](docs/VERIFICATION.md).

Проверки поддерживают опубликованные версии и закреплённые черновики без публикации. Перед стартом сохраняется [готовность стенда и доступов](docs/RUN_PREPARATION.md); ошибки приложения, неточности сценария и невозможность проверки учитываются отдельно.

`make test-ui` запускает постоянный набор Playwright: Chromium, мобильный Chromium, WebKit и обзор в Firefox. Проверки используют отдельную временную схему PostgreSQL и не меняют существующие проекты. `make test-all` объединяет быстрые и браузерные проверки. Подробности и расположение отчётов — в [TESTING.md](docs/TESTING.md).
