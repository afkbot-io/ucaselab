# Развёртывание UCaseLab

## Сервер

Подойдёт Linux с Docker Engine и Docker Compose v2. Практический старт: 2 CPU, 4 ГБ RAM и диск под PostgreSQL и вложения; объём зависит от видео и скриншотов. Установите проект в отдельный каталог. Все команды ниже выполняются из его корня.

1. Создайте DNS-запись домена, например `qa.example.com`, на сервер.
2. Создайте секреты: `python3 scripts/init_env.py`. Файл `.env` имеет права 0600; существующий файл скрипт не перезаписывает.
3. Измените в `.env`:

```dotenv
ENVIRONMENT=production
PUBLIC_URL=https://qa.example.com
COOKIE_SECURE=true
ALLOWED_HOSTS=qa.example.com,api,localhost
HTTP_PORT=127.0.0.1:8080
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_STARTTLS=true
SMTP_USER=noreply@example.com
SMTP_PASSWORD=пароль-из-настроек-провайдера
SMTP_FROM=UCaseLab <noreply@example.com>
```

`POSTGRES_PASSWORD`, `SECRET_KEY` и `ENCRYPTION_KEY` оставьте сгенерированными. Пароль БД генерируется hex-строкой для безопасного использования в URL. В контейнерах DATABASE_URL переопределяется на внутренний сервис `db`.

Для локальной конфигурации порт можно ограничить через `HTTP_PORT=127.0.0.1:8080`. Compose формирует `${HTTP_PORT}:80`, то есть итог `127.0.0.1:8080:80`.

4. Настройте HTTPS перед портом 8080. Например, Caddy на хосте:

```caddyfile
qa.example.com {
    reverse_proxy 127.0.0.1:8080
}
```

Для корректных IP-ограничений входа укажите `TRUSTED_PROXY_CIDR` в `.env`: точный адрес/CIDR, с которого Caddy подключается к Nginx. Для Caddy на Docker-хосте это обычно gateway сети Compose. Его можно узнать командой `docker network inspect ucaselab_default` (поле IPAM.Config.Gateway) после первого запуска. После изменения выполните `docker compose up -d web`. Не доверяйте всем адресам интернета. Nginx заменяет входящий X-Forwarded-For на проверенный адрес клиента; API доступен только во внутренней сети. Без этой настройки лимиты по IP применяются к общему адресу прокси, хотя лимиты конкретного email продолжают действовать.

У Caddy должны быть доступны 80/443 и возможность выдать сертификат домену. При существующем Nginx используйте proxy_pass на 127.0.0.1:8080 и передавайте Host. Для `/mcp/` отключите buffering и установите timeout не менее 300 секунд. Статические ресурсы, API и MCP доступны на одном домене.

5. При установке из Git соберите публичные навыки (в source release они уже включены), затем запустите **основной** Compose:

```bash
python3 scripts/package_skills.py
docker compose up -d --build
docker compose ps
curl -f https://qa.example.com/api/health/ready
```

`migrate` — одноразовый контейнер: код завершения 0 и статус Exited являются нормой. API и worker запускаются только после успешной миграции. PostgreSQL и API не публикуют порты в основной конфигурации. Для production не подключайте `compose.dev.yaml` и `compose.local.yaml`.

6. Зарегистрируйтесь в приложении. Проверьте доставку подтверждения настоящему почтовому ящику. Первый проект создаётся из интерфейса; его создатель — руководитель. Глобального администратора с фиксированным паролем нет.

## Работа без почты

Если письма пока не нужны, установите `EMAIL_ENABLED=false` в `.env`. Новые пользователи регистрируются и сразу входят по email и паролю, без подтверждения владения ящиком. Вход по ссылке и восстановление пароля через письмо отключены; ссылки на них скрыты. Приглашения выдаются как ссылки для ручной передачи, уведомления остаются внутри платформы. Почтовую очередь worker не обрабатывает. Для включения SMTP позже настройте сервер и учётные данные, установите EMAIL_ENABLED=true и перезапустите API/worker. Ранее созданные аккаунты сохраняют доступ.

## Почта

Worker читает транзакционную очередь с блокировкой SKIP LOCKED и повторяет неуспешные доставки с задержкой до 12 попыток. Одноразовые ссылки действуют 30 минут, приглашения — 7 дней. SMTP с STARTTLS поддерживается на 587; используйте провайдера, принимающего STARTTLS. SPF/DKIM/DMARC настраиваются у почтового провайдера и в DNS.

Диагностика: `docker compose logs --tail=100 worker`. В журнал попадают идентификатор события, тип ошибки и номер попытки, без тела письма или пароля. После устранения недоступности SMTP очередь продолжит работу. Для событий с исчерпанными попытками оператор может сбросить `attempts=0` и `available_at=now()` в `outbox_events`; не изменяйте payload. Доставка SMTP имеет семантику at least once: редкий сбой после принятия письма сервером может привести к повторному письму. Использование одноразовой ссылки остаётся однократным.

В локальном режиме:

```bash
docker compose -f compose.yaml -f compose.dev.yaml -f compose.local.yaml up -d --build
```

Почта доступна на http://localhost:8029 и не уходит реальным адресатам. Интерфейс — http://localhost:8080. Для разработки через Vite используются только `compose.yaml` + `compose.dev.yaml` для БД/Mailpit и отдельные процессы из README.

## Обновление

При переходе с версии 1.0 сохраните прежние имена Compose-проекта, пользователя и БД: `COMPOSE_PROJECT_NAME`, `POSTGRES_USER`, `POSTGRES_DB`. Для новой установки они равны ucaselab; у существующей установки значения должны соответствовать прежним контейнерам и томам. Не переименовывайте тома ради смены бренда. Проверьте прежнее имя проекта через `docker compose ls`, а имя БД и пользователя — в вашей конфигурации DATABASE_URL. Ключи SECRET_KEY/ENCRYPTION_KEY сохраняются. Миграция 0002 переименует таблицу планов и добавит словари тегов без удаления кейсов, пользователей или истории.

Перед обновлением создайте резервную копию. Обновите исходники и выполните:

```bash
bash scripts/backup.sh
docker compose up -d --build
curl -f https://qa.example.com/api/health/ready
```

Миграция запускается до API. Начальная схема зафиксирована в миграции 0001; изменения модели в следующих версиях оформляются отдельными миграциями. Проверка новой установки и отсутствия расхождений с моделями: `uv run python scripts/check_migrations.py`. Не используйте `docker compose down -v`: флаг `-v` удаляет данные. Для отката кода оставляйте совместимую версию схемы или восстанавливайте полную резервную копию. Исторические ревизии, публикации, отчёты и завершённые результаты защищены от UPDATE/DELETE триггерами PostgreSQL; обычное удаление проектов заменено архивированием.

## Резервное копирование

```bash
bash scripts/backup.sh /путь/к/защищённому/каталогу
```

Копия содержит `database.dump`, `attachments.tar.gz`, `environment.env` и lockfile зависимостей. Файл environment.env содержит ключ шифрования тестовых аккаунтов и другие секреты. Храните копии в закрытом, желательно зашифрованном хранилище отдельно от сервера. Потеря ENCRYPTION_KEY делает сохранённые пароли невосстановимыми. Не меняйте этот ключ при обычном обновлении.

Скрипт ненадолго останавливает web/API/worker, копирует БД и файлы и возвращает сервисы в работу, в том числе при ошибке копирования. Планируйте этот перерыв в подходящее время. Манифест SHA-256 проверяется перед восстановлением. Регулярно проверяйте копии в отдельном окружении.

Восстановление на подготовленном отдельном сервере: поместите соответствующий `environment.env` как `.env`, при необходимости измените домен/SMTP, сохраните исходный ENCRYPTION_KEY и запустите:

```bash
bash scripts/restore.sh /абсолютный/путь/к/копии --replace-database
```

Операция заменяет текущую БД и вложения. Сначала останавливаются web/API/worker, затем восстанавливаются данные, применяются миграции и запускается приложение. Для нестандартного набора Compose-файлов экспортируйте `COMPOSE_FILE` перед вызовом обоих скриптов.

## Доступ и ограничения

- Cookie сессии HttpOnly и SameSite=Lax; production требует Secure и HTTPS. Изменяющие запросы интерфейса проверяют CSRF и Origin.
- Пароли платформы: Argon2id. Токены: SHA-256 хеш, однократный показ. Тестовые пароли: AES-GCM с отдельным ключом и аудитом раскрытия.
- Scopes MCP дополняют проектные роли. После удаления участника или отзыва токена следующий запрос теряет доступ. Персональный MCP-токен не может выпускать другие токены.
- Вложения скачиваются только после проверки проекта; выдаются как attachment, без выполнения HTML. Размер — до 20 МБ в интерфейсе, до 2 МБ при передаче base64 через MCP.
- Сервер не исполняет присланный JavaScript и не запускает браузеры от имени проекта. Агент тестирует своими инструментами и возвращает факты. Не выдавайте обычному серверу платформы права доступа к Docker socket.
- Отчёты доступны участникам соответствующей аудитории. Публичных ссылок на отчёты в версии 1.0 нет; передача наружу — скачанным файлом.


## Несколько доменов

PUBLIC_URL определяет адрес для создаваемых ссылок. Дополнительные домены перечисляются в ALLOWED_HOSTS, а их точные HTTPS origins — в ALLOWED_ORIGINS. Для каждого имени нужны DNS, собственный сертификат и vhost, проксирующий тот же web-сервис. Wildcard origins не поддерживаются; похожие имена не получают доступ.

```dotenv
PUBLIC_URL=https://qa.example.com
ALLOWED_HOSTS=qa.example.com,qa-secondary.example.com,api,localhost,127.0.0.1
ALLOWED_ORIGINS=https://qa.example.com,https://qa-secondary.example.com
```

Cookie привязана к текущему хосту, поэтому на втором домене нужно войти отдельно. После смены настроек пересоздайте API/worker. Если внутренний IP API изменился, перезапустите контейнер web, чтобы Nginx обновил DNS upstream. Существующие ссылки на основной адрес не переписываются.

## Codex: токен вне config.toml

Создайте в профиле персональный токен с нужными scopes, сроком и allowlist проектов. Сохраните его локально в `~/.codex/secrets/ucaselab.token`: каталог 0700, файл 0600. Не передавайте токен через URL, shell-аргументы или репозиторий.

Локальный helper `~/.codex/mcp/ucaselab-headers.py`:

```python
import json
from pathlib import Path

token = (Path.home() / ".codex/secrets/ucaselab.token").read_text().strip()
print(json.dumps({"Authorization": "Bearer " + token}))
```

В `~/.codex/config.toml` добавьте, подставив абсолютный путь helper:

```toml
[mcp_servers.ucaselab]
url = "https://qa.example.com/mcp/"
http_headers_helper = "/usr/bin/python3 /absolute/path/ucaselab-headers.py"
startup_timeout_sec = 20
tool_timeout_sec = 60
enabled = true
required = false
```

Не запускайте helper вручную с выводом в журнал: он печатает секретный заголовок для клиента. Проверьте регистрацию через `codex mcp get ucaselab`, затем подключение и `get_me` в новом чате Codex. Истёкший токен заменяется через профиль; прежний можно отозвать отдельно. Настройка helper предназначена для локального клиента; облачное окружение не получает локальный файл автоматически. См. [документацию Codex MCP](https://learn.chatgpt.com/docs/extend/mcp).

## Обновление до 1.6.1

Миграция 0003_specification_folders добавляет folders.kind и specifications.folder_id с индексами/ограничением. Существующие папки получают kind=use_cases; существующие спецификации остаются без папки. Идентификаторы, содержимое ревизий и связи кейсов сохраняются.

Перед выкладкой нужна согласованная резервная копия БД, вложений и environment.env по обычной процедуре выше. Этот релиз нельзя откатывать одной заменой приложения на 1.5 после создания папок спецификаций: старый backend не различает разделы. Для полного отката используется резервная копия; downgrade миграции удаляет добавленные папки спецификаций и их расположение.

Перед запуском новой версии выполните backup.sh. Он приостанавливает только работающие web/api/worker и возвращает их прежний состав даже при ошибке дампа. Отключённый почтовый worker не запускается резервным копированием. Результаты развёртывания конкретного сервера фиксируются в закрытом журнале оператора; общая инструкция не является подтверждением выкладки.
