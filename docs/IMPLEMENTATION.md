# Реализованная модель 1.9.2

UCaseLab — платформа юзер-кейсов и проверок. Новая база пустая: пользователи создают свои проекты и данные. За точный контракт отвечают [API_SCHEMA.json](API_SCHEMA.json), `/api/operations` для авторизованного пользователя и схемы MCP tools/list.

## Поиск и выбор элементов

Спецификации, кейсы и аккаунты выбираются через асинхронный поиск с ограниченной выдачей. Теги кейсов, теги спецификаций и платформы хранятся в отдельных словарях проекта. Регистр и пробелы нормализуются; ранее введённые значения остаются доступными QA. Поиск по каталогам, сортировки, фильтры и пагинация одинаковы в REST и MCP. Состояние основных фильтров интерфейса хранится в URL. Общий поиск охватывает кейсы, спецификации, кейс-планы, предложения и аккаунты.

## Сущности

- Пользователи платформы, серверные сессии, одноразовые email challenges, персональные API/MCP-токены.
- Проекты, членство и приглашения; папки с проверкой циклов.
- Юзер-кейс как стабильная сущность; неизменяемая агрегатная ревизия со шагами, вариантами, связями; публикация закрепляет конкретную ревизию. Отдельные таблицы вариантов и M:N связей со спецификациями и аккаунтами.
- Спецификации и их ревизии; тестовые аккаунты с отдельным AES-GCM секретом; окружения.
- Предложения с неизменяемыми ревизиями и пунктами. Принятие набора атомарно создаёт черновики. Публикация остаётся отдельной операцией.
- Версионированные планы. При создании прогона закрепляются plan revision, публикации кейсов, варианты, несекретные данные аккаунтов и конфигурация окружения.
- Прогоны, их элементы, попытки выполнения, результаты шагов, доказательства и добавочные пояснения. Таблица «Проверки» кейса — запрос к этим фактам, без дублирования.
- Обсуждения с привязкой к ревизии и стабильному ключу шага/варианта; плоские ответы, история редактирования, tombstone удаления, завершение/переоткрытие.
- Неизменяемые отчёты, связи с прогонами; JSON/CSV/PDF строятся из сохранённого снимка.
- Уведомления, подписки и настройки, транзакционная почтовая очередь, аудит и ключи идемпотентности.

Исторические снимки и завершённые результаты дополнительно защищены триггерами PostgreSQL. UUID из другого проекта не проходит проверку принадлежности прикладной границы; REST и MCP используют одни операции. Все изменения одного проекта сериализуются блокировкой строки проекта для согласованности публикаций, предложений, планов и конкурентных результатов.

## Роли

| Возможность | Разработчик | Тестировщик | Менеджер | Руководитель |
|---|---|---|---|---|
| Опубликованные кейсы, активные планы, результаты, отчёты проекта | Да | Да | Да | Да |
| Неопубликованные черновики, QA-обсуждения и QA-отчёты | Нет | Да | Да | Да |
| Свои предложения, обсуждения опубликованного | Да | Да | Да | Да |
| Кейсы, папки, публикации, спецификации, аккаунты | Нет | Да | Да | Да |
| Принятие предложений, планы, выполнение, отчёты | Нет | Да | Да | Да |
| Окружения, настройки, инструкции, аудит | Нет | Нет | Да | Да |
| Модерация комментариев с причиной и аудитом | Нет | Да | Да | Да |
| Разработчики и тестировщики в команде | Нет | Нет | Да | Да |
| Менеджеры, передача владения, архив проекта | Нет | Нет | Нет | Да |

В проекте один руководитель — владелец. Передача владения атомарно назначает нового владельца и переводит прежнего в выбранную роль. Его нельзя удалить или понизить обычным редактированием членства. Менеджер не изменяет другого менеджера и самого себя через повышение привилегий.

Чтение и изменение секретов выдаются отдельно от роли; изменение требует как минимум роли тестировщика. MCP дополнительно ограничен scopes, сроком, отзывом и allowlist проектов. Интерфейс редактирования доступен человеку наравне с ИИ.

## Жизненный цикл

1. Тестировщик создаёт кейс или принимает подготовленное предложение.
2. Черновик сохраняется новой ревизией при изменении содержимого. Сравнение показывает изменения полей и перемещения строк по стабильным ключам.
3. Явная публикация делает точный снимок доступным новым проверкам. Существующие прогоны сохраняют старый снимок.
4. План предварительно разрешается в конкретный состав; create_run требует хеш выбранного состава и ожидаемую ревизию плана.
5. begin_run_check атомарно начинает прогон и берёт доступный вариант или возвращает свою текущую проверку. Один общий тестовый аккаунт не выполняется параллельно в двух активных проверках.
6. Записываются наблюдения и доказательства; finish_run_check атомарно фиксирует шаги и итог passed/failed/scenario_issue/blocked/skipped. Для passed нужны passed всех закреплённых шагов. Следующий вариант запускается явно. Корректное отклонение отрицательного ввода — passed.
7. Завершённый результат неизменяем. В активном прогоне можно создать новую попытку; после закрытия нужен новый прогон. Пояснение добавляется отдельной записью.
8. Отчёт фиксирует выбранные прогоны и последние попытки на момент генерации. Дальнейшие пояснения и повторы его не меняют.

## Достоверность результатов

Покрытие: `(passed + failed) / selected`. Успех среди проверенных: `passed / (passed + failed)`, при нуле — не определён. Заблокированные, пропущенные, отменённые и ожидающие выводятся отдельно. Попытки не увеличивают исходный объём плана. Завершённый прогон может содержать ошибки и блокировки; это не подтверждение готовности релиза.

Платформа хранит факты тестирования. Агент получает self-contained execution bundle и использует собственные инструменты браузера/мобильного устройства/API. Чтение кода, генерация скрипта и планирование выполнения сами по себе не дают права записать passed.

## Границы версии

В текущем релизе включён рабочий процесс, описанный выше. OAuth discovery для клиентов без поддержки персональных Bearer-токенов, публичные ссылки на отчёт, собственные размещённые UI/mobile runners, lease pools аккаунтов, ветки с merge и real-time совместный редактор в эту версию не входят. Для них сохранены расширяемые границы исполнения и неизменяемых снимков. Приложение не ведёт внутренние баги.

SMTP выполняется через отдельный worker. PDF/CSV/JSON создаются синхронно из неизменяемого снимка с ограничением до 30 прогонов и 16 МБ снимка на один отчёт. Прогон ограничен 2000 выбранных вариантов и 8 МБ снимков; большие наборы разбиваются на несколько прогонов. Нет притворной фоновой операции со статусом «готово»: операция возвращает сохранённый объект либо ошибку.

## Рабочее место проверки 1.2

Три этапа: подготовка, выполнение, результаты. Слева очередь вариантов с поиском, фильтром состояния и назначения; справа один вариант с данными, ожиданиями и шагами. Итог выбирается явно в отдельном диалоге. Счётчик показывает сохранённые результаты, а не долю успеха. Активный экран обновляется каждые пять секунд без сброса введённого текста. На мобильном очередь раскрывается кнопкой; завершение и остановка требуют явного действия. Список прогонов позволяет создать проверку из опубликованных кейсов или кейс-плана. Новая миграция БД для 1.2 не требуется.

## Контроль результата и альтернативные пути

И finish_run_check, и низкоуровневый record_execution_result требуют явного passed каждого закреплённого шага перед успешным итогом. Пропущенные шаги не считаются успехом. Для публикации активный вариант с собственным путём должен содержать шаги с ожиданиями; ключи шагов одного пути уникальны. Пустые названия и описания обязательных полей отклоняются после удаления внешних пробелов. Значения входных данных и секреты не обрезаются.

## Внимание команды и проверка интерфейса 1.9

Общая навигация показывает личные события, открытые предложения QA и назначенные незавершённые прогоны. Чтение события не закрывает задачу. Видимость списка, счётчиков и почтовой очереди основана на одной SQL-политике текущего доступа, включая понижение роли после создания события. Фоновое обновление использует polling; push-доставки нет.

Меню мобильного устройства открывается модальным диалогом с управлением фокусом. Размеры полей и кнопок, перенос заголовков и панели действий согласованы для узких экранов. Подпись поля отделена от значения textarea и пояснения. Постоянные браузерные сценарии и проверки ролей описаны в [TESTING.md](TESTING.md).

[Каталог документации платформы](qa/catalog.json) содержит спецификации, сценарии и отображение всех операций MCP на функционал. Публикация документации не означает прохождение её вариантов; реальные результаты сохраняются только после выполнения.
